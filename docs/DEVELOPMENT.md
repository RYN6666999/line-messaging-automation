# 開發史：一個「重複貼送」需求如何長成乾淨的兩件式架構

> 本文件按時間序記錄整個真實開發過程。重點不是最終程式，而是**遇到問題時「怎麼想、怎麼驗證、怎麼改」**。
> 每一個階段都標記了：目標 → 遇到的問題 → 我們怎麼推理 → 做了什麼驗證 → 解法 → 教訓。

---

## Phase 0 — 需求與第一版（最小可行）

**目標**：在 LINE 上反覆執行「點擊 → 點擊 → 貼上 → Enter → ↓」，把一份問卷依序發給多位聊天對象。

**第一版**很樸素：`pyautogui.click()` 兩次 → `pbcopy`+`⌘V` 貼上 → `press("enter")` → `press("down")` 換下一位，用 `for` 迴圈重複 N 次。

**教訓**：先給「能跑的最小版」，成功跑通再疊功能 — 避免過早設計。

---

## Phase 1 — 讓「非工程師」真的能跑起來

**問題 1：雙擊 `.py` 沒反應。**
macOS 雙擊 `.py` 只會用編輯器（IDLE）打開，**不會執行**。使用者卡在「根本沒測到就結束」。

**解法**：做**可雙擊的 `.command` 啟動檔**（bash 包住 `python3 script.py`），並 `chmod +x`。
**教訓**：交付物要貼合使用者實際的開啟習慣（雙擊），不是貼最「標準」的做法。

**問題 2：`ModuleNotFoundError: No module named 'pyautogui'`。**
用 `which -a python3` 查出系統有**多個 Python**（`/usr/bin`、`/usr/local`、Homebrew、framework…），每個套件各自獨立。沙箱/我這端的 python 有套件，**不代表使用者終端機的 python 有**。

**解法**：啟動檔固定用「有套件的那個 interpreter 絕對路徑」，並在啟動時 `import` 檢查、缺了就自動 `pip install`。
**教訓**：**「我這端裝成功」證明不了「你那端能用」** — 一定要用使用者真正會跑的那條命令重驗。

**問題 3：能動了但沒效果 → 權限。**
macOS 需要到「系統設定 → 隱私權與安全性 → 輔助使用」授權，且**要 `Cmd+Q` 完全重開**後才生效。

**教訓**：macOS 自動化的第一道牆幾乎都是「權限」，且權限授權對象是「實際跑的那個程序」（終端機 vs IDLE 不同）。

---

## Phase 2 — 一件一件加「安全與可控」

依序加入：步驟間固定 `0.3s` 間隔／「開始前倒數」／**ESC 緊急停止**／**按 Enter 才開始**／左上角 FAILSAFE。

**關鍵技術**：
- `pyautogui` 在 macOS **不能感應鍵盤** — ESC/Enter 偵測要靠 `pynput.keyboard.Listener`（背景守護執行緒設旗標）。
- ESC 停止是在「每輪之間」檢查，當下這一步會先跑完 — 明確告知使用者，而不是假裝即時。

**教訓**：安全功能要「明確、可預期」；每一項都要跟使用者講清楚行為邊界。

---

## Phase 3 — 「LINE 必須在前景」：先用成本意識選方案

**問題**：座標是「絕對螢幕座標」，LINE 不在前景或視窗動了，點擊就會點到別的地方。

**關鍵**：使用者問「確認前景的成本是多少？」→ 我們**實際量測**了兩種做法：

| 做法 | 一次成本 | 給的名稱 |
|---|---|---|
| `System Events`（原本想法） | ≈ 0.74 s | 太貴，跟直接 activate 一樣 |
| `lsappinfo` | ≈ 0.007 s | 只回 ASN 亂碼，要再對照 |
| **Python `AppKit NSWorkspace`** | ≈ **0.0001 s** | 直接給 App 名稱，幾乎免費 |

**解法**：用 AppKit 每個動作前「檢查前景」→ 是 LINE 就零成本跳過；不是（誤點廣告、瀏覽器跳出）才呼叫 `activate` 拉回，並重驗最多 3 次、失敗印警告。
**教訓**：**用「測量」取代「猜測」選方案** — 同樣功能，成本的量級可以差到 7000 倍。

## Phase 4 — 中文輸入法吃掉貼上（`v`／`ㄒ`）與權限錯誤

**問題**：貼上有時只剩一個 `v` 或 `ㄒ`（依輸入法而定）→ 這是 macOS 中文輸入法（注音）把 `⌘V` 吃掉、只剩裸鍵 `v` 敲進注音產生 `ㄒ`。

**錯誤嘗試**：改用 `System Events keystroke "v" using command down` → 在實機上得到關鍵錯誤 **`(1002) not allowed assistive access`** — osascript 沒有輔助使用權限，貼上靜默失敗。

**解法**：回到 **`pyautogui` 手動按鍵**（`keyDown("command") → keyDown("v") → keyUp("v") → keyUp("command")`，全程按住 ⌘），既避開 System Events 的 1002，又把 ⌘ 全程按住、輸入法不容易拆開。
**教訓**：*「看起來更標準」的 API（System Events）不一定適合你的環境* — 用實測錯誤碼（1002）反推根因，比猜更準。

## Phase 5 — 同一人收到一大堆：換人機制與風險

**問題**：跑了之後**同一個人收到一堆**訊息。使用者釐清：他實測 `↓` 就是 LINE 換聊天室的金鑰（推翻了我用「官方預設」猜的 Ctrl+Tab — **使用者實測 > 官方文件**）。但每輪座標固定點回同一聊天室 → 沒真正換人。

**教訓（雙層）**：
1. **不要用自己的泛用知識推翻使用者在真實環境的實測** — 先問、先信實測。
2. **「絕不能讓第一輪就送出真訊息」** — 之後都加測試模式（`DRY_RUN`：只移動、不點不貼）＋單次真跑（`REPEAT=1`、無害文字）＋非重點聊天室，先驗證再放大。

**風險意識**：大量發送前提醒 LINE 限流／風控／帳號風險，並讓使用者「知情選擇」，而不是只會照做。

## Phase 6 —「假成功」：印『完成』但其實沒作用（除錯轉折）

**問題**：明明印了 `✅ 第 N 次完成`，但 LINE 上什麼都沒發生，還出現 macOS 轉圈。

**判斷**：這是**假成功** — 程式只是「流程走完」就印字，**並未驗證動作真的生效**。

**解法**：加入**追蹤 log**（`auto_click_trace.log`）：每一動前後記錄 `frontmost=<App> / mouse=<座標> / 剪貼簿字數`。追蹤結果：
- 每動 `frontmost=LINE` — 證明點擊有打到 LINE、座標正確、剪貼簿 7→188 字成功。
- **但還是沒作用** → 追蹤檔只能證明「事件發到 LINE」，看不到「LINE 內部哪個元件被點到」。

**教訓**：**追蹤資料可以排除「程式端」錯誤，但不能取代「看 UI 現場」**。要往下抓，需要看到畫面（螢幕錄製）或更深的 UI 偵測。

---

## Phase 7 — 標記視窗擋點擊：使用者一針見血的質疑（關鍵轉折）

**當時的情境**：為了「啟動前在螢�幕標出點擊位置、方便對齊」，加了一對**蓋在 (917,529)、(659,811) 上的半透明標記視窗**。

**使用者質疑**：「點擊在 tkinter 是不會作用在 LINE 上的…我才多設計了這個功能後就按不下去了，差在哪？」

**驗證與推理**：
- 追蹤檔仍顯示 `frontmost=LINE`（前景是 LINE）→ 追蹤看似沒問題。
- 但**「前景 App」≠「那個像素上最上面的視窗」**。標記是 `-topmost` 的浮動窗，蓋在點擊座標正上方；若沒被乾淨銷毀，就變成一片**吃掉滑鼠事件的透明瓦片** — 點到的是它，不是 LINE。
- LINE 的「點擊目的」是點掉「太久沒聊天的綠色選取筐」→ 被標記擋住，當然點不掉。

**解法（回歸乾淨）**：**把所有蓋在點擊座標上的標記視窗徹底移除** — 標記/對齊功能整個搬到另一支工具（見 Phase 8）。
**教訓**：**「加功能」若會蓋在關鍵像素上，就可能悄悄摧毀行為**。使用者對自己工具的實際觀察，往往是抓出這類隱性 bug 的最快路徑 — **要認真聽、立刻驗證，而不是辯護**。

---

## Phase 8 — 最終解法：拆成兩件式架構（最乾淨）

把「對齊標記」與「執行自動化」**徹底分離**：

| 工具 | 職責 | 關鍵 |
|---|---|---|
| `mouse_position.py`（測座標） | 只在「對齊階段」顯示標記＋即時座標，ESC 結束 | 標記 `-topmost` 且**每 200ms 重新置頂**（拖 LINE 時不消失） |
| `auto_click.py`（跑auto_click） | **100% 純自動化**：畫面上**絕不掛任何蓋在點擊座標上的視窗** | 嚴格前景確認＋穩健點擊＋貼上＋送出＋緊急停止 |

**為什麼這樣最乾淨**：兩個關注點（「看得見的準備」vs「動手做」）不再互相干擾；使用者「拖動 LINE 視窗導致點擊失效」的問題隨之消失。
**教訓**：**當一個功能的反覆出錯、且難以在本機測試**，平行思考「是不是職責沒分離」— 拆開往往比修更有效。

---

## Phase 9 — 反思：AI 協作下，「問題解決」長什麼樣

這份專案最能呈現的，不是寫得多漂亮，而是**人與 AI 如何合力走完一個真實問題**：

1. **人訂目標、AI 給最小可跑版**：先把模糊需求變成能執行的骨架。
2. **人提供實測觀察、AI 提供查證與測量**：每次可疑行為，都用「讀檔／追蹤／實測」驗證，不憑感覺。
3. **人提出質疑、AI 願意推翻自己的假設**：Phase 7 使用者說「是你加的標記害的」，是整案的轉折點 — 好的協作是**雙方都能被對方說服**。
4. **風險由人承擔、AI 必須提醒**：「第一輪別送出真訊息」「別轟炸同一個人」「LINE 會限流」 — 這些都是 AI 主動把風險講清楚。
5. **收斂到簡單**：最後的答案不是更多視窗、更多 hack，而是 **「拆開」與「讓主程式保持純淨」**。

**一句話總結**：*會用 AI 解決問題的人，不只是「會下 prompt」— 而是能定義好問題、敢質疑、要求 AI 用資料驗證、並把複雜收斂成簡單。*

## 可遷移的技能（面試時可直接講）

- macOS 自動化：`.command` 啟動、多 Python 陷阱、輔助使用／自動化／螢幕錄製權限。
- 事件層：`pyautogui` vs `pynput`、System Events 1002、`frontmostApplication`、IME 貼上。
- 除錯方法：追蹤 log、讀檔驗證、量化方案成本、區分「程式端」vs「UI 現場」。
- 工程態度：測試模式／緊急停止／風險告知／把複雜拆成兩件式。
